# 04 — Window chrome discipline (title + titlebar writers)

**What to build:** The window title is semantic and low-frequency (app name, device, connection state — no live kbps/fps), and no SwiftUI pass mutates window chrome as a side effect. Live telemetry appears only in the stats UI. This removes the audit's candidate self-sustaining invalidation loop (SwiftUI pass → `updateNSView` → async window mutation → geometry invalidation → another pass) and the ~1–2 Hz titlebar relayout churn.

Approach constraints (from the audit):

- Title changes only on connect/disconnect/device change; apply only when the string differs.
- No unconditional `titleVisibility` (or other chrome) writes; compare before writing; no `DispatchQueue.main.async` hop from `updateNSView` for same-value cases.
- Exactly one owner for `titleVisibility` / `toolbar.isVisible` (today both `WindowTitleSetter` and the aspect-ratio coordinator write them).

**Blocked by:** None — can start immediately.

**Status:** in-review — code landed, runtime (diag-build) validation pending with the orchestrator.

**Implementation notes** (all in `Overlook/ContentView.swift`)

- **Who owns the title:** `ContentView.applyWindowTitle(_:)` — a `@MainActor` method that is the only `window.title` writer in the app window path. It compares (`guard window.title != title`) and writes synchronously; there is no `DispatchQueue.main.async` hop. Triggers: `.onChange(of: windowTitle, initial: true)` (state changed) and `.onChange(of: windowRef)` (the `NSWindow` reference arrived after the first body pass — this is where the initial title lands). No `NSViewRepresentable` writes the title any more.
- **Deleted:** `WindowTitleTelemetryHost` (ticket 02's isolation shim — unused once the title dropped telemetry) and `WindowTitleSetter` (whose `updateNSView` unconditionally dispatched async and wrote `titleVisibility = .visible` on every pass — audit finding F4). `.background(WindowTitleTelemetryHost(...))` is off the view tree; `WindowReferenceSetter` still supplies the `NSWindow`.
- **Resolution kept in the title, deliberately:** `WebRTCManager` assigns `videoSize` only when the value actually differs (`if size.width > 0, size.height > 0, videoSize != size`), so it changes on first frame and on guest mode change — connection-level frequency, which the ticket allows. Live kbps/fps/latency now live only in the stats UI (`StreamStatsSection`, `ConnectionLatencyLabel`).
- **Single chrome owner:** `WindowAspectRatioSetter.Coordinator` is now the only writer of `titleVisibility`, `toolbar.isVisible`, `titlebarAppearsTransparent`, `.fullSizeContentView` and `titlebarSeparatorStyle` (audit finding F7's two-owner conflict is resolved). All five go through new `static` compare-before-write primitives (`setTitleVisibility`, `setToolbarVisible`, `setFullSizeContentView`, `setTitlebarAppearsTransparent`, `setTitlebarSeparatorStyle`); `applyFullscreenChrome` / `restoreWindowedChrome` / the one-time configure block all call them.
- **Behavioural delta to watch:** the old code re-asserted `titleVisibility = .visible` on every windowed pass. That re-assert is gone; windowed title visibility now comes from the value stored at coordinator attach (the `.titleBar` default, `.visible`) and restored on fullscreen exit. Pre-existing caveat, unchanged by this ticket: if the window were already fullscreen at attach time, the stored "windowed" values would be the fullscreen ones.
- **Remaining `DispatchQueue.main.async` hops in this file are all pre-existing and non-per-pass:** `WindowReferenceSetter`'s binding write (cannot mutate `@State` during `updateNSView`), the one-time window configure (mutating `styleMask` synchronously inside a SwiftUI update pass re-enters layout), the one-shot initial aspect resize, and the post-fullscreen-exit frame adjust (a window-delegate callback, not a SwiftUI pass).
