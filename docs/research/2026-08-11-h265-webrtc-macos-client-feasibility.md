# Research: H.265/HEVC receive/decode feasibility for a native macOS WebRTC client (Overlook fork → Comet KVM via Janus)

Date: 2026-08-11 · Context: LAB-27 (GLKVM Comet quality) · Client: fork of [rcawston/Overlook](https://github.com/rcawston/Overlook) (Swift + [stasel/WebRTC](https://github.com/stasel/WebRTC) xcframework) · Source: GL-RM1PE Comet (PiKVM/kvmd fork + GL ustreamer + Janus, RV1126B hw encoder, H.264/H.265, 2560x1440@60, ≤20 Mbps)

## Summary

**H.265 receive in a forked Overlook is feasible and is a bounded amount of work — but it is NOT free.** Upstream libwebrtc already ships everything below the SDK line (RFC 7798 depacketizer, `H26xPacketBuffer` frame assembly — and for H.265 that path is enabled unconditionally, *not* behind the `WebRTC-Video-H26xPacketBuffer` field trial, which now gates H.264 only). stasel's prebuilt xcframework is even built with `rtc_use_h265=true`, so those C++ pieces are compiled into the binary you already link. **What is missing is the Apple side: upstream's ObjC SDK has no HEVC VideoToolbox decoder and its default decoder factory advertises only H264/VP8/VP9/AV1** — so declaring an "H265" codec against the stock factory yields no decoder (observed as a runtime crash in LiveKit's SDK). The fork must supply a custom `RTCVideoDecoder` wrapping `VTDecompressionSession` (HEVC) plus a decoder factory that advertises `H265`. Prior art for exactly that patch exists in three forks (WebKit, shiguredo, webrtc-sdk/LiveKit). Two much cheaper paths exist for a *quality decision* before writing code: (a) point Safari at the device with the encoder set to H.265 — WebKit has shipped WebRTC HEVC receive for years and RFC 7798 packetization since Safari 18; (b) accept that the realistic win at 20 Mbps / 1440p60 desktop content is modest, because 4:2:0 chroma — not codec generation — is the dominant limit on text.

## 1. Upstream libwebrtc (Google WebRTC): H.265 receive status

**Shipped, and receive-side frame assembly for H.265 is not field-trial gated.** In current `main`, `RtpVideoStreamReceiver2::UseH26xPacketBuffer()` reads:

```cpp
if (codec == kVideoCodecH265) { return true; }
if (codec == kVideoCodecH264) {
  return env_.field_trials().IsEnabled("WebRTC-Video-H26xPacketBuffer");
}
return false;
```

— i.e. H.265 always uses `H26xPacketBuffer`; the field trial only switches **H.264** off the generic packet buffer. [rtp_video_stream_receiver2.cc (main)](https://webrtc.googlesource.com/src/+/refs/heads/main/video/rtp_video_stream_receiver2.cc) · [h26x_packet_buffer.h](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/video_coding/h26x_packet_buffer.h) · [video_rtp_depacketizer_h265.h](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/rtp_rtcp/source/video_rtp_depacketizer_h265.h) · field-trial registry entry: [experiments/field_trials.py](https://webrtc.googlesource.com/src/+/refs/heads/main/experiments/field_trials.py) (`WebRTC-Video-H26xPacketBuffer`, bug 41480904).

Build gating: outside Chromium the GN arg default is `rtc_use_h265 = proprietary_codecs` (i.e. **off** in a vanilla checkout unless you opt in); inside Chromium it follows `enable_hevc_parser_and_hw_decoder`. [webrtc.gni (main)](https://webrtc.googlesource.com/src/+/refs/heads/main/webrtc.gni). `common_video/BUILD.gn` compiles the H.265 VPS/SPS/PPS/bitstream parsers only under `rtc_use_h265`. [common_video/BUILD.gn](https://webrtc.googlesource.com/src/+/refs/heads/main/common_video/BUILD.gn)

**Chrome milestone: M136, on by default (Windows/macOS).** Chrome's own gating was `--enable-features=WebRtcAllowH265Receive` (+ `WebRtcAllowH265Send`, `PlatformHEVCEncoderSupport`) and `--force-fieldtrials=WebRTC-Video-H26xPacketBuffer/Enabled` up to M135; from M136 no flags are needed. [chromestatus 5153479456456704](https://chromestatus.com/feature/5153479456456704) · [Intent to Ship: H265 (HEVC) in WebRTC](https://groups.google.com/a/chromium.org/g/blink-dev/c/3h8lL8a377c) · [chromium commit 8ca090e (the flag definitions)](https://chromium.googlesource.com/chromium/src/+/8ca090ecf9fcb51daaa549bbce830511b62f00aa%5E%21/) · [webrtc issue 41480904 "Unblock Chrome platform support of H.265 (including H26xPacketBuffer)"](https://issues.webrtc.org/issues/41480904) · downstream confirmation "Browser 136 already supports WebRTC 265… no more need to add the flags": [mediamtx#4536](https://github.com/bluenviron/mediamtx/issues/4536).

**VideoToolbox on macOS: yes in Chromium, no in the standalone ObjC SDK.** Chromium's macOS HEVC decode goes through `media/gpu/mac` VideoToolbox (incl. Main10/RExt profiles: [chromium fd67f82](https://github.com/chromium/chromium/commit/fd67f82ac41ac9a767ef4b344295d13b7206ed75)); the HEVC *encoder* for WebRTC is also VideoToolbox-backed ([chromium 3c22337](https://github.com/chromium/chromium/commit/3c22337112751d92cc004dd52f36a79e2f99aa36)). **But that plumbing is Chromium's, not libwebrtc's ObjC SDK's** — see §2.

## 2. stasel/WebRTC and other prebuilt macOS/Swift binaries

**stasel does build with H.265 enabled.** `scripts/build.sh` sets, for every platform slice:

```
COMMON_GN_ARGS="… rtc_system_openh264=true rtc_use_h265=true"
```

[scripts/build.sh](https://github.com/stasel/WebRTC/blob/latest/scripts/build.sh) · README: "Added support for extra encodings: VP9, H264, H265 (HEVC)" [README.md](https://github.com/stasel/WebRTC/blob/latest/README.md) · the change landed in the M146 release ("New in this version: Support for H264 and H265 (HEVC)") [release 146.0.0](https://github.com/stasel/WebRTC/releases/tag/146.0.0); current `latest` pins M150 [Package.swift](https://github.com/stasel/WebRTC/blob/latest/Package.swift). So an up-to-date stasel build (≥146; use ≥150) contains the H.265 parsers, RFC 7798 depacketizer and `H26xPacketBuffer`.

**The blocker is the Apple SDK layer, not the build flag.** Upstream `sdk/objc/components/video_codec/` contains only H264 files (`RTCVideoDecoderH264`, `RTCVideoEncoderH264`, `RTCH264ProfileLevelId`, `nalu_rewriter`) — there is no `RTCVideoDecoderH265`: [directory listing, main](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/objc/components/video_codec/). And `RTCDefaultVideoDecoderFactory.m` advertises/creates exactly H264, VP8, VP9 and (conditionally) AV1: [RTCDefaultVideoDecoderFactory.m](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/objc/components/video_codec/RTCDefaultVideoDecoderFactory.m). Consequence, reported verbatim against LiveKit's build: declaring an H.265 `RTCVideoCodecInfo` on the default factory "crashes at runtime because there is no actual decoder implementation for H.265" [livekit/client-sdk-swift#734](https://github.com/livekit/client-sdk-swift/issues/734) (also [#710](https://github.com/livekit/client-sdk-swift/issues/710)).

**Therefore, for a stasel-based fork the work is: write an ObjC/Swift `RTCVideoDecoder` HEVC wrapper (VideoToolbox `VTDecompressionSession` + `CMVideoFormatDescriptionCreateFromHEVCParameterSets`, Annex-B→HVCC rewriting mirroring `nalu_rewriter.cc`) and a decoder factory that returns it for `name == "H265"` with `profile-id=1` (matching Janus's fmtp).** Three existing patches to copy from:

| Fork | What it adds | Source |
| --- | --- | --- |
| WebKit's libwebrtc | `RTCVideoDecoderH265.mm` / encoder + RFC 7798 packetization, switchable via a bool on the factories | [WebKit r259452](https://trac.webkit.org/changeset/259452/webkit), [r259568](https://trac.webkit.org/changeset/259568/webkit) |
| shiguredo-webrtc-build | `h265.patch` flips `rtc_use_h265 = true` for non-Chromium and fixes VPS `vps_max_num_reorder_pics` parsing; `h265_ios.patch` adds the ObjC H265 codec-info/profile-level-id files to `sdk/objc` BUILD | [h265.patch](https://github.com/shiguredo-webrtc-build/webrtc-build/blob/master/patches/h265.patch), [h265_ios.patch](https://github.com/shiguredo-webrtc-build/webrtc-build/blob/master/patches/h265_ios.patch), changelog notes "fixed macOS H.265 receive not working" [OLD_CHANGES.md](https://github.com/shiguredo-webrtc-build/webrtc-build/blob/master/OLD_CHANGES.md) |
| HackWebRTC (OWT lineage) | full `RTCVideoDecoderH265.{h,mm}` (277 lines) + `RTCVideoDecoderFactoryH265` | [commit 34c9bd7](https://github.com/HackWebRTC/webrtc/commit/34c9bd7bc4c377f276c3bbe8819708f0fb7d322d) |

**Alternative prebuilt with HEVC already wired for Apple: `webrtc-sdk/webrtc` → `livekit/webrtc-xcframework` (LiveKitWebRTC).** The webrtc-sdk Specs release notes state "Upgrade to WebRTC-SDK M137.7151.03 — **Add H.265 video codec support for Apple SDKs**" [webrtc-sdk/Specs releases](https://github.com/webrtc-sdk/Specs/releases), and LiveKit's Swift SDK changelog lists "HEVC (H.265) codec support" [client-sdk-swift-xcframework CHANGELOG](https://github.com/livekit/client-sdk-swift-xcframework/blob/main/CHANGELOG.md). It is a plain libwebrtc xcframework with `LK`-prefixed ObjC symbols (`LKRTCPeerConnection`) and can be consumed standalone [livekit/webrtc-xcframework](https://github.com/livekit/webrtc-xcframework/). **This is the lowest-code route: swap the SPM dependency and rename symbols, instead of hand-writing a VideoToolbox HEVC decoder.** Caveat: it carries LiveKit-oriented patches (always-on NWPathMonitor field trial, frame cryptor, simulcast patches) and its release cadence is tied to LiveKit; verify the HEVC decoder is exposed through the *default* decoder factory on macOS (not iOS-only) before committing. Also relevant: shiguredo's Sora iOS SDK documents "H.264 / H.265 use Apple VideoToolbox hardware decoder/encoder" [sora-ios-sdk](https://github.com/shiguredo/sora-ios-sdk/), i.e. VideoToolbox HEVC through libwebrtc's ObjC SDK is a proven combination.

Licensing note (worth a conscious decision, not a blocker for personal use): shiguredo distributes H.265-capable binaries only because they confirmed with the patent pools that *hardware-accelerator-only* HEVC use needs no license, and they ship **no** H.265 codec implementation in the binary [webrtc-build README](https://github.com/shiguredo-webrtc-build/webrtc-build/). A VideoToolbox-only decoder path is the same posture.

## 3. Alternative architectures if the libwebrtc route is unattractive

**(a) WKWebView / Safari playback — the cheapest experiment, and near-certain to work.** WebKit has had WebRTC HEVC since 2020 (`webrtc/h265.html` layout test, ObjC H265 encoder/decoder, runtime flag) [r259452](https://trac.webkit.org/changeset/259452/webkit); Safari 18.0 added **RFC 7798 packetization** ("Previously, the WebRTC HEVC used generic packetization instead of RFC 7789 packetization") [WebKit Features in Safari 18.0](https://webkit.org/blog/15865/webkit-features-in-safari-18-0/), [WWDC24 beta post](https://webkit.org/blog/15443/news-from-wwdc24-webkit-in-safari-18-beta/); hardening/regression work on the same code continued through 2024-25 ([PR#19818](https://github.com/WebKit/WebKit/pull/19818), [PR#25159](https://github.com/WebKit/WebKit/pull/25159) — VPS-based reorder-window fix). IETF AVTCORE status slides (July 2024) already recorded "Safari TP: H.265 hardware encode and decode on by default; H.265 WebRTC receive/send on by default" [IETF 120 AVTCORE slides](https://datatracker.ietf.org/meeting/120/materials/slides-120-avtcore-ietf-120-avtcore-wg-meeting-slides-11). Field confirmation: go2rtc was "one of the first projects to support HEVC/H.265 for WebRTC in a browser… Safari is the only browser that supports H265 for WebRTC" (2023) [AlexxIT/Blog#5](https://github.com/AlexxIT/Blog/issues/5). Safari 26.x release notes list WebRTC fixes with no HEVC regressions [Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [26.6](https://webkit.org/blog/18178/webkit-features-for-safari-26-6/).

- **Zero-code test available today**: Janus is the *offerer* here, so with `videoformat=1` (H.265) set on the device, just open the Comet's own web UI in **Safari** — Safari should answer with H265 even though the GL web UI has no H.265-specific code. That gives you an immediate A/B of visual quality before any client work. (Note: the web UI's JS may hard-filter/munge SDP for H264 — if so, force it via `RTCRtpReceiver.getCapabilities('video')`/`setCodecPreferences` in the console, the same trick JetKVM uses, below.)
- **WKWebView caveat**: WKWebView shares WebKit's WebRTC stack, but some media capabilities differ between Safari and embedded WKWebView, and macOS WKWebView WebRTC has had app-specific regressions ([Apple forum 723763](https://developer.apple.com/forums/thread/723763)). Verify empirically; also this reintroduces exactly the webview layer Overlook was built to avoid (input injection, latency, cursor handling) — a hybrid "webview for video only" is architecturally worse than the decoder patch in §2.

**(b) Raw RTP + `VTDecompressionSession` directly.** Technically straightforward for the *decode* half — Apple's HEVC decode path plus RFC 7798 depacketization is well-trodden — but you would be re-implementing ICE/DTLS-SRTP/NACK/RTCP/REMB, which is exactly what makes WebRTC low-latency and NAT-traversing over Tailscale. Not recommended. Prior art to mine for the depacketizer/VideoToolbox glue rather than as an architecture: [steelbrain/IPCamKit](https://github.com/steelbrain/IPCamKit) (pure-Swift RTSP client: "H.264 and H.265/HEVC video — depacketized to AVCC format, ready for VideoToolbox", zero dependencies, Swift 6). A middle option — a Swift-native WebRTC-shaped stack — exists but is immature: [livekit-webrtc-native-swift](https://github.com/MarlonJD/livekit-webrtc-native-swift) (H.264 only today).

**(c) Janus → MSE/fMP4 or LL-HLS.** go2rtc's own comparison table puts MSE latency at "medium" and MP4 at "bad" versus WebRTC "best" [AlexxIT/Blog#5](https://github.com/AlexxIT/Blog/issues/5). For a KVM you are optimizing latency, so this is a regression; only interesting as a fallback. Note Janus's streaming plugin H.265 support has been patchy historically (RTP streaming threads: [H265 on streaming plugin](https://janus.discourse.group/t/h265-on-streaming-plugin/1200), [H265 RTP streaming](https://groups.google.com/g/meetecho-janus/c/Dpdash6lTn4)) — but your device's GL Janus plugin already does H265 packetization + SDP, and Meetecho's own AV1/H.265 work is documented [AV1, H.265 and Janus walk into a bar…](https://www.meetecho.com/blog/av1-h265-janus/), foundation PR [meetecho/janus-gateway#2120](https://github.com/meetecho/janus-gateway/pull/2120).

**(d) Strongest prior art overall — JetKVM shipped exactly this feature.** JetKVM (open source, Rockchip RV1106, same class of device) merged "feat(video): add H.265 codec support with auto-negotiation": HEVC on the hardware encoder alongside H.264, an Auto/H.265/H.264 preference in Settings → Video, and **Auto mode inspecting the browser's SDP offer**, preferring H.265 when supported with fallback to H.264 (Firefox) [jetkvm/kvm#1371](https://github.com/jetkvm/kvm/pull/1371), plus UI capability detection via `RTCRtpReceiver.getCapabilities("video")` looking for `video/H265` [settings.video.tsx](https://github.com/jetkvm/kvm/blob/73a67e88/ui/src/routes/devices.$id.settings.video.tsx), and a follow-up ordering fix (codec must be set before the native pipeline starts) [#1509](https://github.com/jetkvm/kvm/pull/1509). Two things to steal: the negotiation shape, and the observation from the same PR series that **raising the bitrate floor mattered more than codec choice** for perceived quality (base_bitrate_high 2000 → 4000 kbps; H.264 1080p sweeps: factor 0.1 → 3082 kbps, 0.5 → 6357 kbps, 1.0 → 9445 kbps, all 60 fps, ~3-4 ms decode).

## 4. Quality reality check at 10-20 Mbps, 2560x1440@60 desktop/text

**Expect a modest, content-dependent improvement — not a fix for soft text.** Reasons, in order of importance:

1. **You are not bitrate-starved, so codec efficiency buys little.** HEVC's ~35-55% bitrate saving at equal quality is a saving *at the same quality* — it matters when you are on the steep part of the RD curve. At 20 Mbps for 1440p60 largely-static desktop content you are already near the encoder's quality ceiling; your own measurement (6.2-11.5 Mbps observed under a 20 Mbps cap) says VBR is under-spending, i.e. the encoder is not bitrate-limited. Codec-generation numbers for reference: ~44% less bitrate for equal VMAF vs H.264 in aggregate, ranging ~35% (noisy) to >60% (animation) [Fora Soft benchmark summary](https://www.forasoft.com/learn/video-quality/articles-vqm/codec-comparison-real-content); ~2x claim vs measured reality [NASA/Tektronix PQA500 study (PDF)](https://ntrs.nasa.gov/api/citations/20170000636/downloads/20170000636.pdf); Citrix HDX H.264 vs H.265 vs AV1 visual comparison [GO-EUC](https://www.go-euc.com/comparative-quality-analysis-of-citrix-codecs/); an older Citrix H.264-vs-H.265 YUV420 comparison concluding the gain is situational [sschaber.de](http://sschaber.de/2018/01/31/comparison-between-h-264-h-265/).
2. **4:2:0 chroma is the dominant limit on text either way, and H.265 Main profile does not change it.** Both your H.264 and H.265 paths encode NV12 4:2:0 from the RV1126B; coloured text on coloured background loses half the horizontal and vertical chroma resolution regardless of codec. This is precisely why remoting protocols expose 4:4:4 as the "visually lossless"/"high colour accuracy" tier: [GO-EUC: chroma subsampling in remoting protocols](https://www.go-euc.com/chroma-subsampling-and-colour-compression-in-modern-remoting-protocols/), [GO-EUC: 4:2:0 vs 4:4:4 with H.265 in HDX](https://www.go-euc.com/evaluating-the-visual-quality-and-colour-differences-of-fullscreen-h265-video-compression-with-yuv-420-and-yuv-444-in-citrix-hdx/), [NVIDIA remoting-protocol whitepaper (PDF)](https://www.nvidia.cn/content/dam/en-zz/Solutions/design-visualization/solutions/resources/documents1/NVIDIA-vgpu-choosing-the-right-remoting-protocol-whitepaper.pdf) (note how each protocol pairs H.264/H.265 4:2:0 with a *separate* lossless-text or MDRLE path). Microsoft's RDP docs make the same point: "approximately 80% of the graphics data for a remote session is text", handled by bitmap/text-optimised encoders rather than the video codec [Azure Virtual Desktop graphics encoding](https://learn.microsoft.com/en-us/azure/virtual-desktop/graphics-encoding). The real fix for text is 4:4:4 or SCC tooling — HEVC's **Screen Content Coding** extensions (palette mode, intra block copy) deliver the large screen-content wins [MSR: HEVC SCC verification testing](https://www.microsoft.com/en-us/research/publication/verification-testing-of-the-compression-performance-of-the-hevc-screen-content-coding-extensions/) — and an RV1126 hardware encoder does **not** do SCC or 4:4:4.
3. **Where H.265 should genuinely help you: gradient banding.** HEVC Main supports 8-bit only in the profile you'd get, but its larger transform sizes (up to 32x32), better intra prediction (35 angular modes) and the deblocking/SAO pair are materially better at smooth-gradient regions than H.264's 4x4/8x8 transforms — SAO in particular targets banding/ringing. So expect: banding noticeably reduced, fine text *slightly* crisper, chroma fringing on coloured text unchanged.
4. **Cheaper levers first (already identified in LAB-27):** `zero_delay=FALSE` (low-delay rate control is a known quality tax), GOP, and confirming the 20 Mbps cap is actually being spent (REMB throttling over Tailscale/DERP). The WebRTC-codec screen-share comparison also found HEVC's headline advantage on desktop content to be *CPU/efficiency*, with VP9/HEVC close behind AV1 and H.264 the laggard mainly at low bitrate [webrtc-developers.com codec comparison](https://www.webrtc-developers.com/comparison-of-webrtc-codecs-for-video-and-screen-sharing/).

**Verdict:** do the H.265 work for the banding improvement and headroom (it lets 20 Mbps go further, and 4K-capable devices later), not as a cure for text blur. Test before you build, via the Safari route in §3(a).

## 5. Does GLKVM's own "Direct mode" use H.265?

**No — and GL.iNet has explicitly declined to expose H.265 at all, on patent grounds.** In the official forum thread about RM10 "lossless" quality, a user notes the Rockchip encoder can do HEVC ("`mpi_enc_test` shows that there is HEVC (h265) under type 16777220 too and quality switching works. So I guess it is only missing in the UI?") and GL.iNet's reply is: **"H.265 has patent issues, so I cannot provide this option."** [forum.gl-inet.com — RM10 lossless still looks pretty compressed](https://forum.gl-inet.com/t/rm10-loseless-still-looks-pretty-compressed/67090). Corroborating evidence that Direct mode is H.264:

- Your own device recon: `config.json` has `videomode: "directh264"` (LAB-27 comment, 2026-08-11), and the GL web UI contains zero `h265` references.
- GL.iNet's own beta-firmware threads and docs discuss "Direct h264" / "Direct" (HTTP-transported) vs "WebRTC" modes with no H.265 variant, and note Direct mode lacks audio [1.4.0 beta2 thread](https://forum.gl-inet.com/t/new-beta-test-firmware-1-4-0-beta2-for-rm1-comet/61732), [audio only in WebRTC mode](https://forum.gl-inet.com/t/no-audio-setting-in-remote-device-setttings-section/63808), [GL KVM docs: set Transfer = Direct](https://docs.gl-inet.com/kvm/en/faq/remote_screen_goes_blank_no_hdmi_signal/).
- Upstream PiKVM (which kvmd here forks) documents only "WebRTC H.264" and "Direct H.264 or MJPEG over HTTPS" modes [PiKVM Handbook: video modes](https://docs.pikvm.org/video/), [WebRTC H.264](https://docs.pikvm.org/webrtc_config/), [ustreamer H.264/Janus doc](https://github.com/pikvm/ustreamer/blob/master/docs/h264.md).

So the H.265 pipeline on your device is GL's own ustreamer/Janus capability that no shipped GL client uses — consistent with your finding that it is client-blocked, and with the vendor having deliberately left it unexposed. Practical implication: **nobody upstream is testing this path**, so budget for device-side surprises (e.g. missing in-band VPS/SPS/PPS on keyframes — libwebrtc's H.265 depacketizer requires in-band parameter sets, per the upstream commit message "For HEVC, start code is added by depacketizer, and remote endpoint must send sequence and picture information in-band" [a2655449](https://webrtc.googlesource.com/src/+/a2655449ee310704ee2053fd6d43a5ab7002b755)). Also note GL's H.265 patent stance argues you should keep the fork's HEVC path VideoToolbox-only (hardware decode), which is the licensing posture shiguredo validated.

## Recommended sequence (cheapest → most work)

1. **On-device encoder tuning A/B (already queued in LAB-27):** `zero_delay=FALSE`, bitrate 20000, GOP 60, LAN vs Tailscale. Likely the biggest per-hour win.
2. **Safari zero-code H.265 A/B:** set `videoformat=1`, open the device web UI in Safari (force `setCodecPreferences` to `video/H265` in the console if the UI munges SDP). Decide whether the quality delta justifies client work. Measure banding on a gradient and a 100%-zoom text sample.
3. **If yes → swap the SPM dependency to `livekit/webrtc-xcframework` (LiveKitWebRTC)**, whose Apple SDK already has HEVC, and add the `H265` codec to the receiver's codec preferences. Cheapest code path; verify macOS (not just iOS) HEVC decode and the `LKRTC*` symbol rename cost.
4. **If that fails → patch stasel's build**: add `RTCVideoDecoderH265` (port HackWebRTC's 277-line file or WebKit's) + a decoder factory advertising `H265` with `profile-id=1`; stasel already builds `rtc_use_h265=true`, so only the ObjC layer changes. Also carry shiguredo's `h265.patch` VPS `vps_max_num_reorder_pics` fix — WebKit hit the same bug ([PR#25159](https://github.com/WebKit/WebKit/pull/25159)) and it manifests as long time-to-first-frame / hangs.
5. **Mirror JetKVM's negotiation shape** (Auto/H.265/H.264 preference with SDP-capability fallback) so the fork keeps working if the device or Janus regresses.
