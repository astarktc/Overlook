# H.265 decode via stasel/WebRTC bump + hand-written VideoToolbox decoder (Route B)

To receive H.265 over WebRTC from the GL.iNet Comet, we bump the existing `stasel/WebRTC` dependency from 109 to ≥150 (builds carry `rtc_use_h265=true` since 146, so the depacketizer/`H26xPacketBuffer` are in the binary) and hand-write the missing pieces: an `RTCVideoDecoderH265` (VideoToolbox `VTDecompressionSession` wrapper, ported from proven code, carrying shiguredo's `vps_max_num_reorder_pics` fix) plus a decoder factory advertising H265 `profile-id=1`.

**Rejected alternative — swap to `livekit/webrtc-xcframework` (Route A):** verified (2026-08-11, binary disassembly of release 144.7559.11) to expose HEVC decode on macOS through its default factory with zero decoder code. Rejected anyway because: (1) its factory advertises H265 with no `profile-id` fmtp and ships no public H265 headers, so any negotiation fix against the Comet's `profile-id=1` offer means subclassing against private symbols; (2) its binary decoder can't be patched if it carries the VPS reorder-pics time-to-first-frame bug; (3) LiveKit's build patches the audio device module, risking Overlook's custom audio shim (`WebRTCAudioDevice.swift`/`RTCAudioDeviceShim.h`); (4) the LKRTC symbol rename makes future merges from upstream `rcawston/Overlook` painful. The 109→150 API drift is route-neutral (Route A implies the same drift).

**Consequences:** we own ~300 lines of VideoToolbox decode code (unit-tested offline against real Comet bitstream fixtures in the repo); decode is hardware-only (VideoToolbox), which is the licensing posture validated with the HEVC patent pools — never link a software HEVC decoder.
